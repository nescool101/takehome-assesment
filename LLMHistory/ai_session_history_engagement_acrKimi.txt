--- ASSISTANT (message 2) — Core architectural proposal ---
Presented the core architectural move: build a cheap, queryable side-index
(Engagement Registry: engagementId -> firmId, templateId, pinnedVersion,
declinedChangeIds, residencyZone); derive pending-update state from the version
DAG + declined change set; never load an engagement except at accept/apply time
(1 min x 40,000 = 28 days single-threaded at the largest firm — scanning by
loading is impossible).

Cost insight anchoring the doc: invert the naive design. Summaries are generated
ONCE PER PUBLISHED VERSION (~40 publishes/week — trivial inference spend);
the per-engagement fan-out only writes cheap pointer records (DB writes,
milliseconds); the 1-minute load is only needed at backfill and at
accept/decline time. This is also what makes "real time within seconds"
achievable.

Key data structures: version DAG + per-engagement declinedChangeIds, so:
- v7 containing v5's changes: v5-declined portion silently filtered; user sees
  only net-new changes. No re-asking.
- Multiple accumulating updates: pending state is DERIVED
  (baseVersion + latest published non-withdrawn descendant - declined changes),
  not stored per version. Withdrawals = lineage recompute (tombstone offer,
  restore previous pending state).
- At decision time, snapshot exactly what summary the user saw (version pair +
  summary artifact hash) into the decision record = March -> November
  regulatory defense.

Five open decisions posed to the user:
1. Where does the UI read the indicator from? Option A: read Projection store
   directly (engagement system only at accept/decline; seconds-to-indicator
   easy). Option B: materialize inside engagement system (then the 40k x 1-min
   fan-out makes "seconds" impossible — needs ~200 workers just to hit ~3 hours).
   Assistant's instinct: A, with B fallback argument ready.
2. Decline pins change-units (recommended), not versions.
3. Summaries: deterministic templated canonical artifact, immutable + provenance
   (template versions, diff hash, renderer version, timestamp); LLM polish as
   optional display-layer sugar only. Cost is nearly irrelevant at 40/week;
   the issue is audit defensibility + hallucinated change descriptions against
   confidential financial content.
4. Residency: global template catalog (non-confidential, shared); per-region
   (EU/Canada) registry + projections for engagement metadata.
5. Requirement to challenge: "real time — within seconds" — recast as
   "seconds for catalog propagation; indicator read is O(1) fresh or lazily
   derived; engagement-side materialization is best-effort background."

Still missing: firm count and $X value (assistant offered assumed values:

--- ASSISTANT (message 3) — Stack decisions ---
1. Java only — spec says "Implement one narrow component in Java." Kotlin
   coroutines would be nice but signals spec-noncompliance. Java 21 gives ~90%
   of the coroutine benefit anyway.
2. Java 21 + virtual threads, plain blocking code. Reactive (WebFlux/Vert.x)
   is the wrong tool: bottleneck is downstream capacity, not the event loop;
   reactive adds complexity and obscures the backpressure decision the
   reviewers want to see. Pattern: virtual-thread executor + explicit
   Semaphore sized to downstream budget. Do NOT hold all 40k engagements in
   memory — stream/shard + checkpoint.
3. Lambda vs microservice arithmetic: both nearly free at this scale
   (slow path ~50–200 downstream-hours/month; Lambda 1GB ~ $6/mo; Fargate
   0.25vCPU/0.5GB always-on ~ $10–12/mo). Cost doesn't decide; operability
   does. Pick ECS Fargate + SQS over Lambda because: (a) one global semaphore/
   token bucket = trivially correct global downstream protection vs per-function
   reserved concurrency; (b) checkpointing/resumability for 40k-job fan-outs
   is natural in a persistent worker; (c) the assignment asks to demonstrate
   concurrency/failure/idempotency/capacity handling in code you control.
   README should document the Lambda+SQS alternative (reserved concurrency =
   capacity) and why it was rejected — that tradeoff paragraph is graded.
4. LocalStack + Terraform: yes, but ~30 minutes max of the 4 hours.
   docker-compose LocalStack limited to SQS + DynamoDB. One Terraform module
   set with provider override for local (endpoints -> localhost:4566, mock
   creds), envs/local + envs/aws roots, no duplication; OpenTofu fine, don't
   bikeshed. Prefer Testcontainers over hand-rolled LocalStack scripts.
   Explicitly NOT building: EKS, service mesh, Kafka, Step Functions
   choreography, multi-region active-active — each gets a
   "considered, rejected, why" paragraph.
Suggested sequence: lock design decisions 1&2 -> design doc skeleton -> Part 2
code -> minimal infra -> diagrams/polish.

Correction on "30-minute call": the hard constraint is ~1 MINUTE per
engagement load. Stub latency must be configurable; tests run at 10–100 ms.
For load statistics don't burn real time — use Little's Law:
throughput = min(semaphore permits, downstream capacity); wall-clock ≈
jobs x latency / permits. E.g., latency 100 ms, 4,000 jobs (= 40k x 1 min ÷ 10
speedup), 50 permits → ~8 s expected, assert stub never saw >50 concurrent
calls. Proves 40k x 1-min scaling without 667 hours.
